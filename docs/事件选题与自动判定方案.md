## 一、预测事件从哪里来（选题流水线）

### 1.1 总原则

**只上「官方日程可预期 + 官方数据可验证」的事件。** 选题时先回答一个问题：*这个事件截止后，有没有一个公开、权威、能自动读取的数据源可以裁决？* 没有，就不上。

### 1.2 六类选题渠道

| 分类 | 选题来源（官方日程/热点） | 裁决数据源 | 可自动判定度 |
| --- | --- | --- | --- |
| 体育竞技 | 官方赛程表（CBA/NBA/中超 官网赛季日程、比赛日历） | 官方赛后数据面板；体育数据商 API（需授权） | 中：需 API 或稳定抓取 |
| 游戏电竞 | 电竞赛事官方赛程（LPL 等） | 官方赛事数据面板 | 中：需 API 或稳定抓取 |
| 影视娱乐 | 定档日历（猫眼/灯塔专业版）、影片热度榜 | 猫眼专业版票房（**无公开 API，需商务授权**或人工） | 低：优先人工+存证 |
| 科技数码 | 品牌发布会日历（官网/官方微博公告）、新机发布节奏 | 官网参数页、发布会直播 PPT | 中：抓取页面 + 人工确认 |
| 趣味民生 | 中国气象局发布计划、节假日安排、官方数据发布日历 | 中国气象网公开接口、统计局/央行发布数据 | 高：公开 API 直连 |
| 财经宏观 | 央行/统计局/证监会发布日程表 | 官方数据接口（中间价、CPI、PMI 等） | 高：公开接口 |

### 1.3 每日选题 SOP（运营手册）

1. **每日 30 分钟巡览**：官方日程（赛事、发布会、统计发布计划）＋ 热搜/热点榜单，筛出「今天或未来 72 小时内能截止」的事件；
2. **候选事件打分**（满分 100，低于 70 不上线）：
   - 可验证性：有唯一官方数据源、能机读（40 分）
   - 热度：讨论量 / 搜索指数（30 分）
   - 确定性：YES/NO 边界清晰、无歧义（20 分）
   - 时效：24–72 小时内截止，避免拖太久（10 分）
3. **生成判定规范**：按第二节模板填写机读 spec，自动生成用户可见的判定文案；
4. **上线发布**：调用 `createMarket` 云函数（管理员）创建合约，进入 `open` 状态；
5. **归档**：错过或失败的热点进入「明日候选」，已结算合约进入「数据源稳定性档案」（连续判定失败的数据源冻结，不再发新题）。

> 发题前先查数据源注册表（`data_sources`，示例见 [data-sources.example.json](../database/data-sources.example.json)）：**先有数据源，再选题**，而不是先选热题再临时找数据源。

> MVP 阶段建议**每天只发 2–3 条**「高确定性 + 高热度」的题，优先选择有公开 API 的类别（气象、财经、官方统计），把自动判定占比做到 60% 以上，再逐步放量。

## 二、判定条件怎么写（机读 Resolution Spec）

判定条件不能只写给人看，必须写成**机器可执行的 JSON 规范**，由 `resolver` 云函数读取并自动裁决。

### 2.1 六条写作铁律

1. **单一数据源**：只写一个权威来源，禁止“以 A 或 B 为准”；
2. **精确数值**：用 `≥ / ≤ / > / < / ==`，禁止“左右、大概、破 5 亿”这类模糊表述；
3. **明确取数时点**：北京时间精确到分钟（如 `2026-08-09 14:00` 整点）；
4. **明确字段口径**：综合票房还是分账票房、开分还是当前分、整点气温还是日均温；
5. **边界规则前置**：平局 / 临界值 / 数据缺失时的默认判定必须在发题时定死（如：平局判 NO、数据缺失原路退回）；
6. **证据链要求**：自动保存原始响应/页面截图/链接，判定可回溯。

### 2.2 机读规范结构

```json
{
  "version": 1,
  "dataSource": {
    "type": "weather",
    "provider": "中国气象网",
    "url": "http://www.weather.com.cn/data/sk/101010100.html",
    "field": "weatherinfo.temp",
    "transform": "int"
  },
  "condition": {
    "operator": ">=",
    "value": 35,
    "unit": "℃"
  },
  "binaryRule": {
    "missingData": "refund",
    "tie": "NO"
  },
  "evidence": {
    "saveRawResponse": true,
    "saveScreenshot": false
  },
  "humanReadable": "根据中国气象网官方实况，判定时刻北京南郊观象台整点气温 ≥ 35.0℃ 则“预言成功”，否则“预言未成功”。"
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `dataSource.type` | 适配器类型：`api`（通用 JSON 接口）/ `weather`（气象专用）/ `web`（网页抓取，二期）/ `manual`（人工） |
| `dataSource.url / field / transform` | 请求地址、JSON 取值路径（点分路径）、类型转换（int/float/string） |
| `condition.operator / value` | 比较运算符与阈值 |
| `binaryRule.missingData` | 数据缺失时的处理：`refund`（原路退回）/ `NO`（默认判未成功） |
| `binaryRule.tie` | 临界值归属（已在 condition 中表达时可为空） |
| `humanReadable` | 展示给用户的判定文案，由模板自动生成，防止人机文案不一致 |

完整示例见 [database/resolution-spec.example.json](../database/resolution-spec.example.json)。

### 2.3 判定文案生成

运营只填机读 spec，前端展示的“胜负判定标准”由模板渲染：

```
「{provider}」{指标定义}，在 {取数时点} 满足 {运算符}{阈值}{单位} 则“预言成功”，否则“预言未成功”。数据缺失时{原路退回/判未成功}。
```

这样保证「机读规则」与「用户看到的规则」永远一致。

## 三、判定结果怎么做（三层自动化）

### 3.1 判定时间线

```
事件截止 T
   │  lockMarkets（每分钟）锁定市场：停止收注，详情页显示「等待官方判定」
   │  T+5 分钟（等待官方数据刷新）
   ▼
resolver 定时扫描（每 10 分钟）
   ├─ 第 1 层：API 直连 → 自动判定（约 60–80%）
   │     成功 → 证据入库 → status=dispute_window（2 小时昭示，跨夜顺延）
   │     ├─ 无仲裁 → settleMarket 定时器自动结算
   │     └─ 有争议 → 社区仲裁或人工复核 → 覆盖判定或维持
   ├─ 第 2 层：网页抓取 + 截图存证（约 10–20%）
   │     成功 → 同上自动流转
   └─ 第 3 层：重试 3 次仍失败 → 人工复核队列（约 5%）
         运营后台一键确认 → 手动判定录入
```

### 3.2 第 1 层：API 直连（resolver 云函数）

- 云函数 `resolver` 每 10 分钟扫描「已过截止时间 + 带 resolutionSpec + 未进入人工复核」的合约；
- 按 `dataSource.type` 选择适配器：`weather`（气象专用）、`api`（通用 JSON）；
- 自动判定成功后：
  - 市场状态 → `dispute_window`，写入 `result`、`resolvedAt`、`disputeEndsAt`（+2h，跨夜顺延）；
  - 原始响应、取值、判定结果、抓取时间写入 `resolution_logs` 集合（存证）；
- 失败自动重试，连续 3 次失败后标记 `needsManualReview = true` 进入人工队列；
- 之后由现有的 `settleMarket` 定时器（每 10 分钟）自动结算，**全链路无人值守**。

### 3.3 第 2 层：网页抓取 + 存证（二期）

对没有 API 但页面稳定的官方数据源（如官网参数页、赛后数据面板），用无头浏览器（Playwright）按 CSS 选择器取值，并**自动截屏存证**，走同一套判定与昭示流程。抓取器需要维护选择器和反爬策略，因此只用于「高价值 + 页面稳定」的数据源。

### 3.4 第 3 层：人工复核队列（兜底）

- 所有自动判定失败的合约进入运营后台「待判定」列表，附自动抓取的数据快照与错误原因；
- 运营查看数据源后一键确认或修改判定 → 进入昭示期；
- 昭示期内用户可发起社区仲裁（见开发方案）；争议较大时进入人工复核，重判或维持；
- 二期可加陪审团仲裁（文档原方案），彻底把争议交给机制而不是平台。

### 3.5 防错机制（必须）

1. **证据存证**：每次判定保存原始响应/截图、时间戳、数据源版本，可随时回溯；
2. **数据源熔断**：同一数据源连续判定失败 N 次 → 自动告警并冻结该数据源，禁止再发新题；
3. **昭示期兜底**：自动判定同样经过 2 小时异议昭示（跨夜顺延）+ 社区仲裁，不是“机器说了算”；
4. **缺失数据规则**：数据缺失按发题时定死的规则处理（退回或判 NO），避免悬而未决；
5. **审计日志**：`resolution_logs` 全量记录，运营后台可查。

### 3.6 数据源可获得性矩阵（务实建议）

| 数据源 | 类型 | 获取方式 | 可自动判定 |
| --- | --- | --- | --- |
| 中国气象网实时天气 | API | 公开接口，免费 | ✅ 可直接用 |
| 央行人民币中间价 | API/网页 | 官网公开 | ✅ 可接 |
| 国家统计局发布数据 | API/网页 | 官网公开接口 | ✅ 可接 |
| 股市/基金指数 | API | 券商/行情商接口 | ✅ 需授权 |
| 体育赛事比分 | API | 官方/数据商 | ⚠️ 需商务授权或稳定抓取 |
| 电影票房 | API | 猫眼/灯塔专业版 | ⚠️ 无公开 API，需授权或人工 |
| 发布会/官网参数 | 网页 | 官方页面抓取 | ⚠️ 半自动 + 人工确认 |

## 五、数据源分级策略：不需要接入很多 API

### 5.1 核心结论

**自动化判定是效率优化，不是上线前提。** MVP 可以零 API 启动：只发“事实型/排名型”事件，运营在截止后录入一次官方判定 + 官方链接/截图铁证，靠 2 小时昭示期（跨夜顺延）与社区仲裁兜底——这正是原文档的设计。API 只是把高频类目从人工里解放出来，按需分级接入即可。

### 5.2 先按“数据形态”分类，再决定自动化方式

| 数据形态 | 典型例子 | 判定方式 | 自动化难度 |
| --- | --- | --- | --- |
| 数值型 | 气温、汇率、指数、票房 | 数值比较（≥ 阈值） | API 直连或抓取 |
| 事实型 | 是否发布某产品、是否官宣、主队是否获胜 | 一次官方证明（公告/赛果/直播画面） | 人工录入 + 铁证链接，昭示期兜底 |
| 排名型 | 榜单第几名、开分多少 | 官方榜单/评分页 | 一次性截图/链接 |

选题时先判断数据形态：**事实型和排名型根本不需要持续 API**，只需要“截止后取一次证”。

### 5.3 分级接入路线（阶段 0 → 3）

| 阶段 | 做法 | 需要的外部依赖 |
| --- | --- | --- |
| 0（MVP） | 只发事实型/排名型事件；运营录入判定 + 铁证链接；2h 昭示（跨夜顺延）+ 仲裁兜底 | **零 API、零爬虫** |
| 1 | 接入 5–8 个免费官方接口（气象、汇率、官方统计），自动判定高频数值型 | 仅免费公开接口 |
| 2 | 采购 1–2 个数据商（体育数据商、票房数据商各一个），一次覆盖多场景 | 1–2 个付费授权 |
| 3 | 用托管抓取服务处理长尾页面（豆瓣评分、官网参数页） | 1 个抓取服务订阅 |

总量控制：**维护一个约 10–15 个数据源的注册表**就够支撑全部五个分类，而不是“每个平台都接一个 API”。

### 5.4 爬虫限制的对策

1. **低频率抓取**：判定只需要截止时点抓一次并存证，不是持续爬取，被抓风险和维护成本都低得多；
2. **托管抓取服务**：IP 池、页面渲染、验证码交给服务商（ScrapingBee / Apify / 八爪鱼），自己只写取值规则；
3. **能走 API 不走爬虫**：优先官方开放接口和开放数据；
4. **存证优先**：抓到一次就把原始响应/截图存档，后续争议走昭示期和陪审团，而不是反复抓取；
5. **合规意识**：遵守 robots / 服务条款，商用数据优先授权采购，个人敏感数据不碰。

### 5.5 数据源注册表（先注册、后发题）

`data_sources` 集合记录每个来源的形态、授权、稳定性与熔断状态。只有注册过的来源允许发新题；连续判定失败自动标记 `frozen`，禁止继续使用。示例见 [data-sources.example.json](../database/data-sources.example.json)。

## 六、实时赔率（返还倍数）如何计算

### 6.1 赔率不是外部数据，是池子自己算出来的

瓜分池模式下，两侧的“实时赔率”只由**当前双方池子的大小**决定，与任何外部行情、数据源无关：

```
P_total = P_yes + P_no
O_yes   = P_total / P_yes
O_no    = P_total / P_no
```

示例（与小程序/Mock 数据一致）：YES 池 1200、NO 池 800 → 总池 2000：

| 侧 | 池爻 | 返还倍数 |
| --- | --- | --- |
| YES | 1200 | 2000 ÷ 1200 = **1.67x** |
| NO | 800 | 2000 ÷ 800 = **2.50x** |

### 6.2 动态稀释：表态即变化

每次有人表态，其爻进入所选侧池，**该侧倍数下降（被稀释）、另一侧倍数上升**。继续上例：有人再投 YES 300 → YES 1500、NO 800、总池 2300：

| 侧 | 池爻 | 返还倍数 |
| --- | --- | --- |
| YES | 1500 | 2300 ÷ 1500 = **1.53x** |
| NO | 800 | 2300 ÷ 800 = **2.88x** |

界面展示的是“当前预估返还倍数”：如果此刻结算能拿多少。实际结算按截止时的最终池子计算。

### 6.3 支持率与赔率的关系（合规词汇）

```
YES 支持率 = P_yes / P_total = 1 / O_yes
NO  支持率 = P_no  / P_total = 1 / O_no
```

上例：YES 支持率 60%、返还 1.67x；NO 支持率 40%、返还 2.50x。界面可用“支持率/共识指数 + 返还倍数”替代“赔率”一词，与合规脱敏表一致。

### 6.4 边界与规则

- **单侧为 0**：空池一侧倍数显示 `--`；另一侧倍数恒为 `1.0x`（赢家拿回本金、无利可图），天然防止无脑单边下注；
- **结算向下取整**：`floor(投入/胜方池 × 总池)`，余量留在池中，保证爻守恒、平台零赔付风险；
- **平局/数据缺失**：按发题时写死的规则处理（判 NO 或原路退回）；
- **平台不抽水**：虚拟积分模式下总池全部分给赢家（或退回），平台只做撮合。

### 6.5 赔率与判定是两个独立系统

- **赔率只决定“赢家怎么分”**（瓜分比例）；
- **判定才决定“谁是赢家”**（由前三节的数据源三层自动化产出）；
- 两者互不耦合：赔率随表态实时变化，判定只在截止后发生一次。

## 七、AI 大模型能参与什么（接入大模型 API 的正确姿势）

### 7.1 一句话结论

**可以接入大模型 API，但只能当“助理”，不能当“裁判”。** 简单地把判定交给 LLM 说一句话出结果，是错误且危险的用法。

### 7.2 AI 能做的（推荐接入）

| 环节 | AI 做的事 | 人工/规则兜底 |
| --- | --- | --- |
| 选题发现 | 输入官方日程、赛事赛程、发布会日历、热搜榜单，输出候选事件清单（含热度与可验证性打分） | 运营逐条确认后进入发题 |
| 判据起草 | 把候选事件改写成 YES/NO 题目 + 判定条件草案（数据源、字段、阈值、边界规则） | 运营核对数据源真实性后发布 |
| 数据解析 | 给定「抓取到的官方数据快照」（JSON/页面文本），让 AI 提取数值或判断字段含义 | 原始快照必须存证，结果可人工复核 |
| 异常辅助 | 自动判定失败时，AI 分析错误原因并给出修复建议（改选择器、换字段等） | 修复后仍走正常判定流程 |

### 7.3 AI 不能做的（红线）

1. **不能做最终裁决**：LLM 会“幻觉”——编造结果、编造链接、编造数据，无法作为平台信任基础；
2. **不能替代证据链**：判定必须可回溯（官方接口响应、截图、链接），LLM 的回答不具备存证性质；
3. **不能绕过昭示与仲裁**：即使 AI 参与解析，仍要走 2 小时昭示期（跨夜顺延）+ 社区仲裁兜底；
4. **合规风险**：预测市场的裁决必须客观、可验证、可审计，把裁决权交给生成式模型在法律与声誉上都站不住。

### 7.4 推荐架构：LLM + 工具调用（Function Calling）

```
运营提问/定时任务
   ↓
aiAssistant 云函数（接大模型 API）
   ├─ 选题助手：拉取官方日程/热点 → LLM 生成候选事件（人确认）
   ├─ 判据助手：生成题目 + resolutionSpec 草案（人确认）
   └─ 解析助手：只读「已抓取的官方数据快照」→ 输出取值建议
        （LLM 不联网记忆，只做阅读理解；原始快照一并存证）
   ↓
规则引擎 / 运营复核 → 最终判定 → 昭示期 → 自动结算
```

关键点：**AI 只读取“我们抓到的官方数据”，不依赖它自己的记忆**；最终判定仍由数据源规则（resolver）或人工确认产出。

### 7.5 落地建议

- 第一步先做「**AI 选题助手**」：运营后台加一个按钮，输入“本周热门事件”，AI 返回候选清单，运营勾选后进发题流程——这一步风险低、价值立现；
- 第二步做「**判据起草助手**」，把发题表单里的标题和判定说明自动填充；
- 判定环节保持“规则 + 人工”，AI 只做解析失败时的辅助；
- 国内环境建议接入国内合规大模型（通义千问、DeepSeek、文心一言等），API Key 配置在云函数环境变量中，不写进前端。

如果你确认接入哪家大模型，我可以把「AI 选题/判据助手」做成运营后台里的一个可运行功能。

> 已实现（2026-08）：**AI 选题助手**、**批量发题**与 **AI 起草判定条件**均已接入 DeepSeek——`aiSuggestTopics` 根据运营需求生成候选事件清单（含可验证性标注），多选后进入批量发题页，逐条 AI 起草判定草稿、统一审核后一键批量创建合约；`aiDraftSpec` 返回结构化 `resolutionSpec` 草稿自动填充表单。AI 只能引用已注册数据源、只起草规则与选题建议，不参与裁决。启用步骤见 README「启用 AI 功能」。
