## 一、总体评价

**这个项目的基础质量明显高于同类 MVP 平均水平**，尤其在资金一致性与工程纪律上：

- 事件状态机严谨（`open → locked → dispute_window → resolved` + 仲裁支路），结算锁 + 崩溃接管阈值设计正确；
- 发钱口全部做了幂等/原子保护（签到 CAS、破产补助 CAS、广告回调 transaction_id 去重、单注事务结算、bets 主键天然防重）；
- 定时触发器 7 个全部配置齐全，前端有竞态守卫、骨架屏、分页加载；
- 内容安全做了 msgSecCheck + 本地词表双保险且不再 fail-open；
- 文档（开发方案/部署清单/判定方案）与代码同步度高。

但审查发现 **2 个必须立即修复的 Bug（P0）**、6 个逻辑/安全问题（P1）、若干性能与冗余问题。以下按优先级展开。

## 二、P0：必须立即修复

### P0-1 广告服务端回调发放必然失败（缺 `_` 定义）
**文件**：`cloudfunctions/adRewardCallback/index.js:100`

`grantAdReward()` 内使用了 `_.inc(amount)`，但文件头部只声明了 `const db = cloud.database()`，**从未定义 `const _ = db.command;`**。SSV 回调一旦触发，事务内必抛 `ReferenceError: _ is not defined`，奖励发放永远失败（仅 console.error，回调方仍收到 `is_valid: true`）。

```js
// 第 20 行后补上：
const _ = db.command;
```

### P0-2 被邀请人 +100 新手能量不落库（幻影奖励）
**文件**：`cloudfunctions/login/index.js:120-125`

注册事务内只写入 `INIT_POINTS(1000)`；事务提交后 `user.points += INVITEE_POINTS` **只改了内存中的返回对象，没有任何数据库写入**。用户看到 1100，重新登录后变回 1000。

```js
// 修复：把加成合并进事务内的 set
await t.collection('users').doc(OPENID).set({
  data: Object.assign({}, user, {
    invitedBy: inviteFrom,
    points: INIT_POINTS + (inviteFrom ? INVITEE_POINTS : 0)   // ← 落库
  })
});
```

## 三、P1：逻辑与安全缺陷

### P1-1 邀请人每日上限被双倍消耗
**文件**：`login/index.js:87` + `placeBet/index.js:78-88`

- 注册时：`inviteRewardToday + 1`（占 1 个名额，此时**没有发任何奖励**）；
- 被邀请人首次表态时：再次 `dailyUsed + 1` 判断并占用名额发奖。

一次有效邀请消耗 **2 个**日限额，实际每日上限只有配置值（10）的一半；且注册占了名额、被邀请人始终不表态时，名额不退还。建议：注册时不占名额，只在 placeBet 发奖时占用（用 `_.inc(1)` 配合条件更新）。

### P1-2 广告回调信任客户端透传的发放金额
**文件**：`adRewardCallback/index.js:146-151`

`amount = Number(info.reward_amount)` 来自小程序端 `setServerSideVerificationData` 的透传数据（`task.js` 传的是 `AD_TASK_POINTS`）。改包客户端可把它改成任意值，微信服务器会原样透传。服务端应**忽略该字段**，固定使用 `AD_TASK_POINTS = 100`。

### P1-3 `togglePkOpen` 返回值污染全局用户对象
**文件**：`pages/profile/profile.js:210-222`

云函数返回 `{ ok: true, user }`，但页面 `.then(user => { getApp().globalData.user = user; this.setData({ user, ... }) })` 把**整个响应体**当成用户对象写入 globalData。后果：「我的」页数据短暂错乱，且 `share.withInvite()` 取 `user._id` 失败 → 此后分享的链接**丢失邀请码**（直到下次 login 刷新）。

```js
// api.js 中统一解包即可：
togglePkOpen: data => call('togglePkOpen', data).then(res => res.user),
```

### P1-4 榜单快照与周期清零同刻触发，存在竞争
**文件**：`rankSnapshot/config.json`（每天 00:00）与 `resetPeriods/config.json`（周一/每月 1 号 00:00）

两个定时器同一时刻触发，SCF 不保证执行顺序。若 `resetPeriods` 先把 `weekPoints` 清零、`rankSnapshot` 后跑，则**本周最终榜快照全为 0**，周榜荣誉（历史 Top10 判定）与「排名变化箭头」数据丢失。建议：快照改为 23:55，或清零延后到 00:05，或把两者合并为一个函数内串行执行。

### P1-5 `settleMarket` 批量分支无调用方校验
**文件**：`settleMarket/index.js:265-275`

带 `marketId` 的分支校验了管理员，但**无参批量分支任何用户都可调用**，会扫描并结算所有到期市场。业务结果与 cron 一致（不会提前结算），但可被恶意刷调用消耗云资源配额。建议批量分支加 `SOURCE !== 'wx_client'` 或管理员校验。

### P1-6 `hasDispute` / `disputeCount` 是死字段
**文件**：`settleMarket/index.js:258,268`

全库检索：**没有任何代码把 `hasDispute` 置为 `true`**，`disputeCount` 也从未递增。「存在申诉需人工复核」分支永远不会执行。要么补上「申诉/异议」功能（公示期内用户对判定提异议 → 置 `hasDispute=true` → 转人工复核队列），要么删除这两处判断避免误导维护者。

## 五、冗余/一致性问题

1. **配置三处口径不一致（重点）**：
   - `config.js` `DISPUTE_WINDOW_MS = 12h`（注释写「默认 12 小时」）；
   - 服务端 `resolveMarket`/`resolver` 默认 **5h**（`DISPUTE_WINDOW_HOURS`）；
   - `profile.js` 规则弹窗文案写死「12 小时异议公示期」；README 写 5h。
   → 前端 `DISPUTE_WINDOW_MS` 实际未被服务端使用（纯展示残留），建议删除前端该配置，文案统一从一处取。

2. **邀请配置重复定义**：`config.js` 与 `constants.js` 各有一份 `INVITE_INVITER_POINTS / INVITEE_POINTS / DAILY_CAP`，签到/广告常量也在 `constants.js` 与各云函数内硬编码两份（checkIn、claimAdTask、adRewardCallback 各自硬编码）。改数值时极易漏改其中一处 → 建议收敛为「前端 constants.js 唯一，云函数走环境变量 + 缺省值」，并在部署清单里登记。

3. **云函数公共代码大面积复制**：敏感词表/注入校验在 `updateProfile`、`createArbitration`、`createMarket` 各存一份；`todayKey()` 重复 6 处；`ADMIN_OPENIDS` 解析重复 8 处；`computeDisputeEndsAt` 重复 2 处。CLI 部署不支持子目录是已知限制，建议用「单文件共享模块 + 构建脚本拷贝」或 npm 私有包治理。

## 七、云服务设计审查

**肯定的**：状态机、结算锁（含 stale 接管）、单注事务、快照荣誉、超时转人工、webhook 告警、SSV 回调协议实现（验签+AES 解密）都是生产级思路。

**需要补齐**：
- **数据库安全规则未在仓库中体现**：`users`、`bets`、`pks`、`arbitrations` 必须在控制台设为「仅创建者可读写」或「所有用户不可读写」（全部走云函数）。建议在 `database/` 增加 `security-rules.md` 或在部署清单中逐项列出每个集合的规则截图核对项；
- **resolver 数据源 URL 无白名单校验**：目前只有管理员能录入（createMarket 有注册表校验），风险低，但注册表本身（`upsertDataSource`）建议加 URL 域名白名单防 SSRF 误配；
- **订阅消息** `thing1/2/3` 字段需与公众平台模板严格一一对应，未配置时静默跳过——上线前用真实模板 ID 做一次端到端验证；
- **监控告警缺失**：云函数失败率、resolver 连续失败、结算锁 stale 接管次数都没有告警出口，建议接企业微信机器人（lockMarkets 已有 webhook 雏形，可推广到 settleMarket/settleArbitration 的失败分支）；
- **数据备份**：bets/users 是资金账，建议开启云数据库定时备份或每日导出。
