# 预测卦局 · 事件监控与判定能力完善方案（2026-08-14）

> 本方案整合以下来源：外部《热点二元投票事件结果监控与结算系统实施方案》V1.0（`uploads/事件结果判定方案.txt`）的**方法论**、对本项目代码的逐行审核结论、以及热榜公开 API 的**实测结果**。
> 核心约束：**不引入自建后端**（排除 Python/FastAPI/PostgreSQL/Redis/Celery/Docker 方案），全部能力在微信云开发（云函数 + 云数据库 + 定时触发器）内增量实现。

## 一、第一期：判定能力增强（最高优先，约 1 周）

目标：把「只能判 API 数值题」扩展到「官方网页/公告类事件」，缩短判定时效，堵住信息套利。

### 1.1 resolver 新增 webpage 适配器（零依赖）

当前 `resolver` 只有 `api`（generic-json）与 `weather` 两个适配器。新增 `webpage`：

```js
// resolutionSpec.dataSource 示例（type=webpage）
{
  "type": "webpage",
  "url": "https://official.example.com/result",
  "regex": "开奖号码[:：]?\\s*([0-9]+)",   // 方式一：正则提取（零依赖）
  "selector": ".result-num",               // 方式二：简单 CSS 选择器（仅支持 #id/.class/标签名，零依赖）
  "transform": "int|float|string"          // 提取后类型转换
}
```

- **提取方式**：① `regex` 正则捕获组；② `selector` 简单选择器（`#id` / `.class` / `tag`，内部用正则实现，不引入 cheerio）；③ 都不配则全文文本
- 抓取前剥离 `<script>/<style>/标签`，只保留可见文本（防噪音干扰匹配）
- 判定走现有 `evaluate(actual, condition)` 规则引擎，结果与证据（原文前 5000 字符）写入 `resolution_logs`
- 失败/未匹配 → 计入 `resolutionAttempts`，连续 3 次转人工复核（复用现有通道）

### 1.2 多源交叉验证 backupSources

`resolutionSpec` 增加可选 `backupSources[]`（1~2 个，类型 api/webpage）：

- 主源判定成功后，逐个拉取备用源判定
- 任一备用源结果与主源**一致** → 确认（证据记录各源结果）
- 备用源**全部失败** → 以主源为准确认（主源可信度更高）
- 任一备用源**不一致** → 视为来源冲突 → **转人工复核**（不自动结算）

### 1.3 时间戳防信息套利（结果提前揭晓检测）

`resolutionSpec.dataSource` 增加可选 `timestampField`（数据源返回结果的时间戳字段，如 `data.publishTime`）：

- resolver 判定时，若配置了 `timestampField`，读取该字段并与 `market.deadline` 比较
- **结果时间 < 截止时间** → 疑似「结果在收注期间已存在」→ 转人工复核，不自动结算
- 未配置 `timestampField` → 跳过（兼容现有数据源，行为不变）

> 说明：真正严格的「结果提前出现 → 立即封盘」需要实时监控（外部方案第 8.2 节），一期先做**判定侧拦截**——结果提前出现在数据源时拒绝自动结算，改人工核验，同时管理端告警。

### 1.4 锁定时立即判定（时效）

`lockMarkets` 每轮锁定到期市场后，**立即调用 `resolver` 触发判定**（云间调用 `cloud.callFunction`），把「结果出现 → 判定」从最长 ~15 分钟（10 分钟周期 + 5 分钟 grace）压缩到 ~1 分钟。保留定时器兜底（resolver 每 10 分钟仍运行）。

### 1.5 发题规则扩展

`createMarket`：
- `SOURCE_TYPES` 增加 `webpage`
- 校验 `backupSources[]`（类型白名单、url 必填、与主源不得同 url）
- 校验 `timestampField`（若配置，须为合法点分路径）
- `expectedResultAt`（可选字段，预期揭晓时刻）：入库 + 管理端复核队列按此排序展示

## 二、第二期：热点发现与选题供给（约 1 周）

目标：让「AI 选题」从「运营手动触发」变为「持续自动供给」。

### 2.1 定时选题云函数 dailyHotTopics（新建）

- **触发**：每天 08:00 / 20:00（`config.json` 定时触发器）
- **流程**：
  1. 拉取稳定免费源：GitHub Trending（`api.github.com/search/repositories?q=created:>7d&sort=stars`）+ Hacker News（`hacker-news.firebaseio.com/v0/topstories.json` + 每条 item 详情）
  2. 聚合为「今日热点素材」文本（标题 + 摘要 + 链接）
  3. 调用 `aiSuggestTopics`（`searchOnly:true` + 素材作为 `searchSummary` 预置）→ 生成候选
  4. 候选写入新集合 **`topic_candidates`**（status: pending / accepted / rejected，含分类/标题/理由/数据源建议/建议截止时间/来源证据）
  5. 管理端告警（飞书/企微，复用 `LOCK_WEBHOOK_URL`）
- **失败兜底**：任一源失败不影响整体（逐源 try/catch）；全部失败记日志
- **幂等**：按 `date` 去重（同日不重复生成）

### 2.2 稳定数据源补充

`data_sources` 注册表新增（`database/data-sources.import.json` 同步）：

| 名称 | type | url | 用途 |
|------|------|-----|------|
| GitHub Trending | api | `https://api.github.com/search/repositories` | 科技数码类选题/判定 |
| Hacker News | api | `https://hacker-news.firebaseio.com/v0/` | 科技/趣味类选题 |

### 2.3 管理端「定时候选」

- 新云函数 `getTopicCandidates`（管理员）：按日期倒序返回 `topic_candidates`
- `suggest` 页新增「定时候选」区块：展示候选列表，支持勾选进入现有「批量发题 / 单个发题」流程（复用 `goBatch`/`goPublish`）

## 四、热榜公开 API 实测记录（2026-08-14）

| 候选 | 实测 | 结论 |
|------|------|------|
| api.guole.fun（dailyhot-api 公开实例） | 403 Forbidden（openresty 拒绝） | ❌ 不可用 |
| dailyhot.imsyy.top | 连接失败 | ❌ 不可用 |
| rankslive.com | 超时 | ❌ 不可用 |
| dailyhot-api.vercel.app | 超时 | ❌ 不可用 |
| api.github.com/search/repositories | 200 / 1.3s | ✅ 用 |
| hacker-news.firebaseio.com/v0 | 200 | ✅ 用 |
| v2ex.com/api/topics/hot.json | 空响应 | ⚠️ 弃用 |
| s.weibo.com/top/summary | 302（反爬） | ⚠️ 不做 |

**结论**：热榜聚合类**公开实例**不可作为生产依赖（免费服务随时挂/限流/地区限制）；改用**官方稳定 JSON API**（GitHub/HN）+ 现有 AI 联网搜索双通道。

## 七、范围外（明确不做）

- 秒级体育/行情（云函数定时器分钟级；确有需求再评估 HTTP 触发器/外部回调）
- 自建全网搜索引擎 / 大规模社交抓取 / 未授权财经行情
- 政治、社会、高争议事件的自动判定（维持人工审核）
- 与现金/兑换/分成挂钩的竞猜形态（合规红线）
