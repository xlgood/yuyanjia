## 一、微信认证（解锁分享）——上线前必做

### 1.1 背景

小程序**未认证**时，微信禁用转发/分享能力：`open-type="share"` 按钮点击直接弹「由于小程序未完成认证，分享功能暂时无法使用」，右上角「···」转发同样失效。**邀请裂变是本产品核心增长机制，分享是命脉**——不认证 = 裂变链路完全不可用，只能靠搜索/扫码进入。

### 1.2 选项对比

| 选项 | 费用 | 能力 | 限制 | 适配度 |
|------|------|------|------|--------|
| A. 个人主体认证 | 30 元/年 | 解锁分享/订阅消息/大部分基础能力 | 无微信支付（本项目无支付，无影响）；**类目范围窄**，需确认「娱乐-趣味测试/趣味互动」个人可申请 | ✅ 推荐 |
| B. 企业主体认证 | 300 元/年 | 全部能力 + 更宽类目 | 需营业执照 | 规模化后 |
| C. 不认证 | 0 | 分享禁用 | 裂变不可用 | ❌ 不可行 |

### 1.3 关键风险与前置确认

1. **类目匹配是前提**：微信个人主体类目有限。需先在公众平台「设置 → 服务内容声明 → 类目」确认「娱乐-趣味测试/趣味互动」或「工具」是否在个人可选列表；若不在，则只能走企业主体（或调整产品定位）。
2. **占卜类内容红线**：认证审核会查内容。当前已做的合规弱化（卦友/雅号/娱乐声明/弱化占卜联想）就是为此准备，认证前建议再过一遍 `node scripts/check-compliance.js`。
3. 认证通过后分享**自动解锁**，代码零改动（`open-type="share"` + `onShareAppMessage` + 邀友码路径均已就绪）。

### 1.4 落地步骤

1. 微信公众平台 → 设置 → 基本设置 → 微信认证 → 提交资料（个人：身份证 + 30 元；企业：营业执照 + 300 元）→ 审核 1~7 个工作日
2. 审核前自查：`npm run check` 全绿、`check-compliance.js` 前端 0 命中、真机过一遍无报错
3. 认证通过后：真机验证详情页/邀请页分享按钮弹出微信转发界面 → 走一遍「A 分享 → B 打开（带 inviteCode）→ B 首开 +10 → B 首次表态 → A +5」完整裂变链路
4. **认证期间过渡方案（可选）**：`miniprogram/utils/config.js` 加 `APP_CERTIFIED: false`，未认证时隐藏 `open-type="share"` 按钮（避免用户点到官方报错），认证后置 `true` 恢复

## 二、更正后积分回滚规则——建议维持现状

### 2.1 背景澄清（重要）

当前状态机**已经挡掉了大部分更正风险**：`resolveMarket` 只允许在 `open / locked / dispute_window` 状态改判，**`resolved`（已结算）后无法改判**。而 `dispute_window` 是结算前的昭示期——此时改判**还没有用户拿到积分**，不存在「追回已发放积分」的问题。

所以真正的决策点是：**要不要支持「结算后更正」（已发积分需回滚/补偿）**？

### 2.2 选项对比

| 选项 | 机制 | 风险 | 成本 | 建议 |
|------|------|------|------|------|
| A. 维持现状（结算后不可改判） | 判定错误靠「2 小时昭示 + 社区仲裁」在结算前纠正；结算即终局 | 极少数结算后才发现的问题无法纠正（但昭示+仲裁已显著降低概率） | 0 | ✅ MVP 推荐 |
| B. 结算后更正 + 积分回滚 | 改判 → 重新结算 → 赢变输/输变赢 → 追回/补偿 → 二次昭示 | **高风险**：用户可能已花掉爻（追回失败）、负余额处理、刷分漏洞 | 高（资金审计 + 二次结算 + 防刷） | 二期评估 |
| C. 结算后更正仅标注不回流 | 改判 + `resultVersion+1` + 页面/记录标注「历史判定已更正」，已发积分不变 | 低（无资金流动）；历史结算与最新判定不一致（靠标注解释） | 低 | 若 B 不可行，可选 C |

### 2.3 推荐路径

1. **现在拍板：维持 A**。判定终局性 = 资金安全的第一原则；昭示期 + 仲裁已提供纠错通道。
2. 已就绪的审计基础（无需新开发）：`resultVersion +1`、`resolution_logs` 完整证据、更正通知（若未来开 B/C，通知机制现成）。
3. **二期评估触发条件**：若运营反馈「结算后错误」出现频率显著（如月 > 5 起），再开会评估 B 或 C；届时优先 C（标注不回流）试点，B 需风控评审。

### 2.4 验收（当前状态）

- 昭示期改判：`resultVersion` 递增 ✓、已表态用户收到「结果已更正」✓（需订阅模板）
- 已结算市场：`resolveMarket` 返回「该卦题已结卦」✓（终局保护生效）

## 三、素材源商业授权——MVP 坚持免费源

### 3.1 背景

定时选题已接入 6 个**免费官方源**（GitHub/HN API + IT之家/36氪/少数派/新浪 RSS）。外部方案建议的体育/财经付费源（Sportradar/Opta/Wind 等）成本数百~数千元/月。

### 3.2 成本对比

| 方案 | 月成本 | 覆盖 | 判定时效 | 说明 |
|------|--------|------|---------|------|
| 免费源 + webpage 页面判定 + 人工录入（当前） | ~0 | 科技/财经/民生 + 官方页面类 | 分钟级 | resolver 的 webpage 适配器已就绪，官方页面（豆瓣开分/交易所公告/统计局）无需付费 API |
| 免费源扩展（找更多免费 RSS/官方页） | ~0 | 逐步拓宽 | 分钟级 | 按「实测可用」模式在 `RSS_SOURCES` 加源即可 |
| 付费体育 API（Sportradar 等） | 数百~数千元 | 体育全覆盖 | 秒级 | 需授权 + 合规评估 |
| 付费财经行情 | 视供应商 | 行情全覆盖 | 秒级 | 商业用途必须授权，未授权接口有法律风险 |

### 3.3 推荐路径

1. **MVP（现在）**：维持免费源三件套——免费 RSS/API 选题 + webpage 官方页面判定 + 人工录入兜底。新增源按「实测 200 + 稳定」标准扩展。
2. **触发付费源的条件**（满足其一再评估）：① 体育/电竞类目正式上线且被用户高频使用；② 免费源判定失败率 > 20%；③ 有广告/付费收入模型可覆盖数据成本。
3. 若上付费源：优先**单一供应商**（一个源覆盖篮球/足球/电竞，减少集成与授权成本），合同明确「仅用于展示/判定，不可分发」。

## 四、判定时效（秒级）——分钟级够用，秒级按需

### 4.1 现状与目标差

| 环节 | 当前 | 目标（外部方案） | 差距 |
|------|------|-----------------|------|
| 截止 → 锁定 | ~1 分钟（lockMarkets 每分钟） | 即时 | 可接受 |
| 锁定 → 判定 | ~1 分钟（锁定即触发 resolver） | 30s~3min | ✅ 已达标 |
| 结果出现 → 判定 | 取决于数据源刷新（分钟级） | 30s~3min | 数据源侧，非系统侧 |

**结论：当前链路已满足方案 25.3 的时效目标（官方数据发布后 1~3 分钟内判定）**。秒级（30s 内）主要对体育赛事有意义。

### 4.2 选项对比

| 选项 | 机制 | 成本 | 适用 |
|------|------|------|------|
| A. 保持现状（分钟级） | 当前链路 | 0 | ✅ MVP |
| B. resolver 周期 10 分钟 → 1~2 分钟 | 改定时触发器 Cron | 0（调用量 1440/天，成本可忽略） | ✅ 推荐现在做（低成本提升容错，锁定即触发失败的兜底更快） |
| C. 秒级轮询（HTTP 触发器 + 外部 cron 每 30s 调） | 开通云开发 HTTP 访问服务 + 免费外部调度（如 Vercel Cron）每 30s 触发 resolver | ~0（免费层），复杂度中等 | 体育类目上线后 |
| D. 数据源 webhook 回调（秒级 + 精准） | 付费体育 API 提供商推送结果 → HTTP 触发器 | 需付费源 + 回调开发 | 上付费源时配套 |

### 4.3 推荐路径

1. **现在**：执行 B——`resolver`/`settleMarket` 等定时触发器周期压到 1~2 分钟（改 `config.json` + 控制台同步），零成本提升容错。
2. **秒级触发条件**：体育/电竞类目正式上线且用户强依赖时效 → 评估 C（免费轮询）或 D（付费 webhook，配合第三节决策）。
